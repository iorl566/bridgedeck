# 视觉模块：要不要另接模型

> 背景：桥已经把"测量 + 执行 + 校验"做完（网格/剖面/区域放大、区域相对坐标、命中校验、一步式 `visual-drag`）。
> 剩下的只有一步：**看图判断"目标在哪"**。这篇只回答一个问题——这一步要不要在桥里另接一个模型。

## 1. 业界的三条路

| 路线 | 代表做法 | 谁来"看" | 代价 |
| --- | --- | --- | --- |
| **纯视觉定位** | [Midscene.js](https://midscenejs.com/model-strategy.md) 一类工具：截图直接喂 VL 模型，模型输出元素坐标，不依赖 DOM | VL 模型 | 要模型（API 或本地部署）；有调用成本与延迟；截图离开本机 |
| **DOM + 标注截图** | Playwright/Puppeteer 封装、Set-of-Marks：把可交互元素编号画在截图上，模型只选编号 | 模型（弱视觉需求） | 依赖 DOM；Canvas / 自绘控件直接失效 |
| **本地专用 CV/OCR** | [ddddocr](https://pypi.org/project/ddddocr-1.6.1/) 一类：`slide_match` 直接给缺口坐标 | 小模型（离线） | 只解决特定题型；要 Python + 依赖；准确率随站点变化 |

关键差别在"谁来读图"：前两条把读图外包给模型，自动化脚本里没有 agent；第三条只针对验证码这一类窄场景。

## 2. 我们的判断依据

1. **有没有 agent 在环**。有 agent 时，agent 本身就是多模态模型，再塞一个模型是重复投入；无人值守时才有必要。
2. **桥的价值在哪**。桥的不可替代性是"测得准、算得准、校验得住"，不是"认识图里有什么"。模型能力会逐年变强，把能力绑进桥里会很快过时。
3. **隐私与依赖**。截图可能含用户数据；把图片发到外部 API 是新增的数据流向。项目一直维持"运行时零依赖、只连本机"，这两条都不该为了验证码破掉。
4. **合规边界**。桥不内置"某个站点验证码怎么解"的知识；识别能力和站点知识分开，用不用、怎么用由使用者决定。

## 3. 决定：桥不接模型

**桥不内置视觉模型，也不做 OCR/打码。** 桥只负责三件事：

- 把画面截清楚（区域截图 + 自动放大 + 网格 + 剖面）；
- 把坐标换算准（区域相对 → 页面坐标，归一化）；
- 把动作校验住（派发前命中校验、单次消费、截图后几何复测）。

"看懂"这一步留在外面：agent 看图、或人看图、或将来外挂一个视觉服务。

## 4. 若将来要无人值守，按适配器外挂

统一契约：

```
输入：PNG 路径 + 可选提示（目标描述 / 候选区域）
输出：{ x, y } 或 { dx }（图片像素坐标）
```

- 桥只认这个契约，不关心背后是本地 CV、VL API 还是别的；
- 调用侧加一个 `--locate` 开关：给定提示，先调适配器拿坐标，再执行；
- 顺序可配：本地 CV 优先（快、免费）→ 失败走 VL API → 再失败回落 `request-help` 人工；
- **适配器不进桥本体**，协议面不需要为它改动。

## 5. 将来第一步做什么

先做**本地 CV 的滑块缺口匹配**（边缘模板匹配 + 候选打分）。理由：已有 PNG 解码（`tools/image-inspect.mjs`）和差分剖面，缺的只是匹配打分；零依赖、可离线验证，还能直接拿现成靶场的拼图题做评测。只有"本地 CV 覆盖不了的题型比例高"时，才值得引入外部模型。

## 6. 一句话

**要不要另接模型，取决于有没有 agent 在环。** 现在有，所以不接；要接也接在适配器层，不进桥。
